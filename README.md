# 二簡字·拼音 — 一個基於 Rime 的二簡字輸入方案

以《第二次漢字簡化方案（草案）》（中國文字改革委員會，1977年12月20日）所擬字形為輸出的
Rime 輸入方案。該方案已於 1986年6月24日由國務院明令廢止，此處僅供研究與存檔之用。

```
打 tingzhi  →  仃止〔停止〕
打 canting  →  歺厅〔餐厅〕
打 zhidao   →  知辺〔知道〕
打 kedou    →  科斗〔蝌蚪〕
打 menglong →  𰰡龙〔朦胧〕
```

---

## 一、設計思路

二簡字最棘手的兩點，你一開始就點出來了：**字表難找**，以及**二簡與一簡非一一對應**。
實際做下來，第二點的解法決定了整個架構。

### 1. 不建二簡詞庫，而是在「候選漢字」層面轉換

最直覺的做法是造一部「拼音 → 二簡字」的詞庫。這條路是錯的。

二簡大量採用**同音代替**，借用的那個字往往另有本音本義：

| 一簡 | 二簡 | 借用字的本音本義 |
|---|---|---|
| 嘴 zuǐ | 咀 | 咀嚼的咀讀 jǔ |
| 停 tíng | 仃 | 伶仃的仃讀 dīng |
| 遇 yù | 迂 | 迂迴的迂讀 yū |
| 橘 jú | 桔 | 桔梗的桔讀 jié |
| 韭 jiǔ | 艽 | 秦艽的艽讀 jiāo |

若造詞庫把「咀」標成 zui，打 `jujue` 就再也出不了「咀嚼」——輸入法被二簡污染了。

本方案改走 **OpenCC 過濾器**：詞庫仍是現行簡化字的朙月拼音，
轉換發生在**候選漢字生成之後**。於是：

- 打 `zui` → 候選「嘴」→ 過濾為「咀」 ✓
- 打 `jujue` → 候選「咀嚼」→ 表中無此詞，原樣輸出 ✓

一簡與二簡的讀音分歧被天然隔離。上面五條註釋（皆出自《草案》原文註）因此**全部自動成立**，
一條規則都不用寫。

### 2. 由字到詞：靠最長匹配，而非逐詞枚舉

你擔心詞語的對應關係複雜。結論是：**二簡本質上是字形改革，不是詞彙改革**，
絕大多數詞只要逐字替換即可。OpenCC 的 mmseg 分詞是「從左起取最長匹配」，
所以只要把少數詞級例外放進同一張表，長鍵自動優先於短鍵：

```
蝌蚪	科斗        ← 詞級規則，優先
蒙	𰰡            ← 字級規則，兜底
```

打「蝌蚪」得「科斗」，打「蒙古」得「𰰡古」，各行其是。

一二表共 57 條詞級規則，分三類來源：

1. 《草案》原文即以詞為單位列出者（哔叽→毕几、霹雳→辟历、蚯蚓→丘引、朦胧→𰰡龙…）；
2. 原文註釋規定的義項分化，主要是 **註七**：「雕刻的雕簡作刁，老雕的雕簡作 𩾗」——
   故 `雕刻→刁刻` 而 `座山雕→坐山𩾗`；
3. 本方案補入的鳥名詞條（見 `tools/curated.json`）。

### 3. 一對多 / 多對一

- **多對一**（丁叮盯釘 → 丁）：寫的方向毫無歧義，`uniquifier` 把塌縮後重複的候選併掉即可。
  實測見下「歧義體檢」，損失遠比預期小。
- **一對多**（同一字依義項有不同二簡形）：以 OpenCC 多值條目表示，Rime 會列為並排候選。
  目前有兩條：`雕 → 刁 / 𩾗`，`雪 → 𫜹 / 彐`。

### 4. 過濾鏈

朙月拼音預設輸出繁體，而二簡表吃簡體，故須串接：

```
朙月拼音（繁） → simplifier(t2s) → simplifier@erjian_* → uniquifier
```

```bash

```

## 三、使用

四檔輸出，`Ctrl+\`` 選單切換，或 **`Ctrl+Shift+6` 循環**
（librime 對單選開關組的 toggle 即「循環到下一項」，並自動互斥，故一個鍵夠用；
`Ctrl+Shift+1`～`5` 已被 Rime 預設佔用，勿改用）：

| 檔位 | 內容 | 完整度 |
|---|---|---|
| 一簡 | 現行簡化字，不轉換 | — |
| 二簡·一表 | 第一表（試行表）。1978 年曾在《人民日報》等出版物上短暫試用 | 與錄文逐條比對，無缺漏 |
| 二簡·一二表（二表 Unicode 未編碼字從闕） | 第一表＋第二表 | 第二表原擬 605 形，本表 206 形 |
| 二簡·修訂（1981 另擬） | 1981 年《第二次漢字簡化方案（修訂草案）》 | 原件 119 原字，本表 99 個 |

**前三檔是累加的，第四檔不是。** 一表 ⊂ 一二表；但「修訂」自成一套，不含一、二表。

第三檔原先叫「二簡·全表」，那是不實的標籤：第二表逾三分之二的字形至今未進 Unicode，
根本無從輸入。改稱「一二表」只表範圍，缺口交給括注。確切分布見下文「完整度」。

### 修訂草案為什麼獨立成檔

1981 年的修訂草案是對 1977 年草案的**刪減重擬**，不是增補。本方案的資料比對如下：

| 修訂表 109 條的來源 | 條數 |
|---|---|
| 也見於第一表 | 77 |
| 也見於第二表 | 24 |
| 兩表皆無（新增） | 8（舨 覆 蝌 鬎 嘹 滕 舀 腴）|

1977 年一二表共 577 條，修訂草案只留下 109 條。另有 10 條**改動了字形**：

| 原字 | 1977 | 1981 |
|---|---|---|
| 巅 癫 | 𱂪 | 颠 |
| 镰 | 连 | 𰾮 |
| 潦 | 了 | 𣱾 |
| 藤 | 滕 | 𣳾 |
| 鑫 | 欣 | 𨥖 |
| 襟 | 𥘞 | 衿 |
| 蠹 | 𫊥 | 𧉓 |
| 翼 | 𰭝 | 𮊾 |
| 解 | 𭷔 | 觧 |

既有刪、又有改，疊加在一二表之上會得出一個歷史上不存在的字表，故獨立。
括注「另擬」即為此意。

### 修訂草案的完整度（據原件核算）

已取得一手文獻：**《第二次漢字簡化方案修訂草案征求意見表》，中國文字改革委員會，1981 年**，
維基共享資源掃描本（8 頁，公有領域）。維基文庫只校對了第 2 頁，第 3–8 頁由本專案據掃描件
轉錄「原字」欄，存於 `data/xiu_1981_yuanzi.json`。

原件分兩部分：

| 部分 | 條目 | 原字 |
|---|---|---|
| 一、不作簡化偏旁用的簡化字 | 91 | 99 |
| 二、可作簡化偏旁用的簡化字 | 20 | 20 |
| 合計 | **111** | **119** |

91＋20＝111 正合「修訂草案收簡化字 111 個」之說 —— 可見**那個數字指條目，不指字形**，
且不含類推字（原件未枚舉）。本方案此檔 113 條 ＝ 119 個原字中的 99 個 ＋ 類推字 14 個
（鼾 撼 憾 溜 榴 瘤 腴 悴 啐 碎 粹 醉 翠 瘁）。

仍缺 20 個原字：贛 罐 毀 疆 韁 僵 沒 膻 嚏 臀 贏 粵 纂 鬼 冀 蒙 鼠 叟 夷 雨。
多數是 1981 年**另擬的新字形**，原件說明中明言「現改作」，而該形至今無碼位。

#### 據原件補入的四條

`矗→𰅹`、`具→𰋙`、`真→𰅴`、`直→𰅰`。原件列此四條而 honoka55 表失收，依兩重論證補入
（每條的完整依據見 `tools/curated.json`）：

**其一，證 Unicode 所收即 1977 年之形。** 以 CHISE IDS 核對構件組成，並反查確認無第二個
碼位符合該形。以 `矗` 為例，原件說明作「仿轟（轟）、聶（聶）等字簡化。直旁按 𰅰（直）
類推簡化」，而 IDS 顯示 轟=`⿱车双`、聶=`⿱耳双`、`𰅹`=`⿱𰅰双` —— 同時滿足「X＋双」與
「直旁作 𰅰」兩項條件。`具/真/直` 則共用且形構件 `𠀃`，且 1977 年的類推字
（俱=`⿰亻𰋙`、顛=`⿰𰅴页`、值=`⿰亻𰅰`、矗=`⿱𰅰双`…）全部建於其上，字族自洽。

**其二，證 1981 年未改此形。** 原件的編輯體例是凡改動者說明中必有「現改作」字樣
（二之4 冀、二之9 蒙、二之3 鬼、一之50 沒皆然），此四條皆無。另有旁證：原件一之13
（巔癲）的說明引用「真旁按真（𰅰）類推簡化」，1981 年的文件自身仍在使用真之簡化形。

只補這四條本字，**不外推類推字** —— 原件第二部分只列偏旁、不枚舉類推。巔癲一條的存疑
亦未處理。

「簡作」欄未轉錄：1981 年鉛印字形須逐字比定 Unicode 碼位，憑掃描件目驗指派碼位風險過高，
故從闕。本次核算只用「原字」欄，那一欄都是常用字，辨識無虞。

#### 一條存疑

原件條目 13 的說明作：「顛是巔癲的本字，合併後不會引起岐義。**真旁按真（𰅴）類推簡化。**」
依此，1981 年的 巔/癲 應作「顛」且其 真 旁再按 𰅰 類推，結果仍得 `𱂪` ——
與 1977 年同形，而非 honoka55 表所記的 `颠`。本方案暫從 honoka55，存疑待考，
詳見 `data/xiu_1981_yuanzi.json` 的 `_notes`。

候選右側 `〔…〕` 內是轉換前的現行簡化字，可當讀音與原字的提示。

## 五、字表來源與校勘

### 底本

- **中國文字改革委員會：《第二次漢字簡化方案（草案）》，1977年12月20日。**
  錄文據維基文庫：<https://zh.wikisource.org/wiki/第二次汉字简化方案（草案）>
- 字形的 Unicode 對應取自 honoka55 的 erjian-convert 專案：
  <https://github.com/honoka55/erjian-convert>（MIT）

### 校勘

已將 honoka55 的第一表與維基文庫錄文逐條比對（`python3 tools/validate_ws.py`，見 `tools/`）：

- 維基文庫 273 條，honoka 278 條，**無一條缺漏**；
- honoka 多出 5 條，皆屬合理增補：`懂→㤏`（由 `董→苳` 類推）、`晴→𰕺`
  （維基文庫錄文此處空缺，因該字形至 Unicode 13.0 新增扩展 G 區才獲編碼）、
  以及三條本就合併列出的詞條（曚昽／朦胧／蒙眬→𰰡龙）；
- **分歧一條**：`雪`，維基文庫作 `𫜹`(U+2B739)，honoka 作 `彐`(U+5F50)。二者字形有別，
  本方案以原文形 `𫜹` 為預設，`彐` 列為並排備選。

### 未採信的材料

honoka55 另有一張 2 410 條的反向（二簡→一簡）解碼表，初看很誘人——
把它反轉似乎能白撿 2 000 多條詞級規則。實測不可行：該表**跨表合併**
（`镰→连` 出自第二表而 `镰→𰾮` 出自修訂草案，混在一處），且對同一字存在兩種相反約定
（既有 `邦→帮`，又有 `友帮→友邦`）。反轉後 278 條「詞級例外」中絕大多數是這類假象，
另有 `蘖孽→𰰟` 一類條目其實是「𰰟 可讀作蘖或孽」的釋義，根本不是詞。故全部棄用，
詞級規則改以《草案》原文與原文註釋為據。

## 六、完整度

逐類清點（`python3 tools/validate_ws.py`、`derive_leitui.py`）：

| 部分 | 應收 | 已收 | 缺 | 缺的原因 |
|---|---|---|---|---|
| 第一表 | 248 | 278※ | 0 | — |
| 第二表 前七類 | 269 | 224 | 96 | 字形至今無 Unicode 碼位 |
| 第二表 簡化偏旁類推 | 339 | 30 | 309 | 見下 |

※ 第一表實收數高於原文自述的 248，因含類推字與詞級規則條目。

**第二表前七類沒有遺漏**：凡維基文庫錄文給出碼位的，全部收錄；「有碼位卻漏收」為 0。

**類推字是真正的缺口**，分兩種：

- **簡化偏旁本身無碼位**（約 230 字）：隹 50、耳 30、皿 27、雨 19、其 13……
  偏旁都沒碼位，類推字更不可能有。且這些組一個類推字都沒收，無從反推偏旁字形。無解。
- **偏旁有碼位、類推字未收**（82 字）：見下節。

### 類推字補全（IDS 推導）

原理是構件替換後反查碼位：`谏 = ⿰讠柬`，第二表把偏旁 `柬` 簡作 `𫠣`，
故二簡形 = `⿰讠𫠣`，反查得 `𫍝`。資料用 [CHISE IDS](https://github.com/chise/ids)
（`IDS-UCS-*.txt`，涵蓋 URO 及擴展 A–J）。

比對分三層強度：

| 層 | 比對方式 | 用途 |
|---|---|---|
| exact | 未歸一的展開式 | 證據最強，偏旁變體也須一致 |
| loose | 歸一後的展開式 | 容忍 `纟`/`糸`、`礻`/`示` 之類記法差異 |
| bag | 葉構件多重集，不管版式 | 僅供人工判斷，**不採納** |

以表中已有的 28 個類推字作留出驗證：**命中 28，推錯 0**（exact 18、loose 9、bag 1）。

產出則很少：82 個候選只推出 **1 個**——
`褴 = ⿰衤监 → ⿰礻监 = 𱵥` (U+31D65)，IDS 完全吻合，已採納。

`bag` 層另給 3 個候選，核對後全是誤配，未採納：

| 原字 | 應為 | bag 候選 | 候選實際 IDS | 判定 |
|---|---|---|---|---|
| 慨 | ⿰忄旡 | 㤅 | ⿱旡心 | 「愛」的古字，無關 |
| 煦 | ⿱昫一 | 𠳉 | ⿰口⿱旬一 | 不符 |
| 煞 | ⿺⿱刍一攵 | 𭣰 | ⿰⿱刍一攵 | 版式不符，存疑 |

其餘 81 字推不出，即該字形**不在 Unicode 內**（CHISE 涵蓋到擴展 J，可信）。
按組分佈：灬→一 35、舟→𠔾 14、旁→㝑 8、衤→礻 5、𠦝→车 4、敢→攼 3，餘零星。
`灬→一` 一組幾乎全軍覆沒，因為二簡常順帶改動版式
（`杰 ⿱木灬` 的二簡形是 `𣎶 ⿰木一`，由上下改為左右），單純替換構件推不出來。

結論：**字表已接近 Unicode 所能表達的上限**，剩下的缺口不是資料蒐集問題，
而是那些字形從未被編碼。

## 六、已知侷限

1. **未編碼字**。《草案》全案收簡化字 853 個，本方案只能處理已進入 Unicode 者。
   三張表實收 278 / 592 / 109 條。缺口的確切位置見下節「完整度」。
2. **分段輸入時詞級規則可能失效**。過濾器拿到的是單個候選。一次打「眼蒙眬」得「眼𰰡龙」；
   若分兩次打「眼」「蒙眬」，第二段仍命中 `蒙眬→𰰡龙`，結果相同；
   但更長的跨候選詞組規則則無法生效。
3. **`simplification` 開關須保持「简体」**。關掉它，過濾器拿到的是繁體，
   只有繁簡同形的字會被轉換，得到繁／二簡混雜的結果。
4. 二簡本身是**有損**的。見下。

### 歧義體檢

用朙月拼音詞庫 19 881 個常用詞實測（`python3 tools/selftest.py`）：

| 表 | 轉換後不同字形數 | 發生同形合併的組數 |
|---|---|---|
| 第一表 | 19 866 | 15 |
| 一二表 | 19 853 | 28 |

即 **99.86% 的詞轉換後仍彼此可分**。且合併掉的那十幾組，絕大多數本就是異體詞：
了帳/了賬、柑桔/柑橘、祕笈/祕籍、彷徨/徬徨、暴露/曝露、旋渦/漩渦、太阿/泰阿……
這正是「同音代替」想要的效果。真正有損的只有屏棄/摒棄、忿懣/憤懣等寥寥數例。

換言之：**多對一在「寫」的方向上幾乎不成問題**，問題全在「讀」的方向——
而那不是輸入法要解決的事。

## 七、檔案結構

```
erjian.schema.yaml      輸入方案
opencc/
  erjian_b1.{txt,json}    第一表        278 條
  erjian_b12.{txt,json}   第一表＋第二表 592 條
  erjian_xiu.{txt,json}   1981 修訂草案 113 條
data/erjian_tables.json 原始字表（保序鍵值對，含重複鍵）
tools/
  build_tables.py       由原始字表生成 opencc/*，含校驗
  curated.json          人工校訂層（覆蓋／增補／多候選），每條註明依據
  selftest.py           31 條黃金用例 + 歧義體檢
  check_font.py         本機字體覆蓋檢查
  validate_ws.py        與維基文庫錄文比對
  derive_leitui.py      用 IDS 推導簡化偏旁的類推字
data/derived_leitui.json  推導結果
install.sh              安裝並重新部署
```

### 改字表

**不要直接改 `opencc/*.txt`**，那是生成物。改 `tools/curated.json`，然後：

```bash
python3 tools/build_tables.py && python3 tools/selftest.py && ./install.sh
```

`curated.json` 的 `add` / `remove` **必須指明表名**。第一表與第二表所簡化的字並不相同——
`雕→刁` 只屬第二表，若不分表，鳥名詞組就會漏進第一表，使「座山雕」在第一表檔
錯誤地轉成「坐山𩾗」（正解是「坐山雕」：`座→坐` 屬第一表，`雕` 不簡化）。
`override` 則只改已存在的條目，因而自動只作用於收了該字的表。

`build_tables.py` 有兩項校驗值得一提：

- **級聯合成**。OpenCC 是單遍最長匹配，不像逐條正則替換那樣反覆套用。
  故詞級規則的輸出必須預先合成到不動點：`座山雕` 的規則若只寫成 `座山𩾗`，
  `座→坐` 就會漏掉，正確結果應為 `坐山𩾗`。此類問題原表中有 5 處，已自動修正。
- **純淨輸出**。OpenCC 的 text 詞典**不支援 `#` 註解行**。檔首多一行註解，
  OpenCC 便解析失敗，而 librime 只會籠統報 `opencc config not found`，
  極難排查（本專案就在此處卡過一次）。故 `.txt` 只寫條目。
